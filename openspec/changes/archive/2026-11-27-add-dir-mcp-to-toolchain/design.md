# Design

## Context

`scripts/setup.sh` installs each pinned tool into `.tools/bin`, fetching
through `FETCH_VERIFIED`, which fails closed unless the URL has a SHA-256 line in
`scripts/lib/checksums.txt`. URLs come from `scripts/lib/assets.sh`
(`ASSET_TOOLS` and `asset_url`), shared with `scripts/tools/update_checksums.bash`.
`shfmt` is the closest precedent: a raw binary, not an archive. See proposal.md
for the motivation.

`dir-mcp` differs from every other tool in one way: it is a stdio MCP server and
prints nothing for `--version`, `-v`, `version` or `-h` (probed on the
`v1.3.8-mcp.1` darwin-arm64 asset), so the existing drift check
(`version_matches "$(tool --version)" "$PIN"`) cannot be used for it.

Release `v1.3.8-mcp.1` publishes `mcp-server-{darwin,linux}-{amd64,arm64}`,
exactly the four platforms in `SUPPORTED_PLATFORMS`, plus `*.sigstore.json`
bundles. Both `v1.3.8` and `v1.3.8-mcp.1` tags exist; the compose files run the
`1.3.8-mcp.1` image.

## Goals / Non-Goals

**Goals:**
- One `task setup` gives a machine the same `dir-mcp` the compose stack runs.
- The existing safety properties hold for it: pinned version, pinned SHA-256,
  no download piped into a shell, reinstall on version drift.

**Non-Goals:**
- Verifying the sigstore bundles on every `task setup` (needs network, a TUF
  fetch and a Python tool each run); verification happens once, at pin time (D5).
- Adding `cosign` or any other new binary for verification.
- Changing how the recruiter finds the binary (`shutil.which`) or its error text.
- Windows (`mcp-server-windows-amd64.exe`); the toolchain supports darwin and
  linux only.

## Decisions

**D1. Extend the repo toolchain, not a per-agent setup step.** `dir-mcp` goes
through the same pin, checksum and install machinery as every other tool, so
Renovate, `task tools:checksums` and the setup tests already know how to handle
it. Alternatives considered: a step in the recruiter's own Makefile (a second
download path with its own trust story, invisible to `task setup`); extracting
the binary from the `ghcr.io/agntcy/dir-mcp` image (needs Docker, and the image
is a different artifact than the one the code's error message points at).

**D2. Pin `1.3.8-mcp.1`**, matching the compose image, with the release tag
`v1.3.8-mcp.1`. `asset_url dir-mcp` builds
`https://github.com/agntcy/dir-mcp/releases/download/v${DIR_MCP_VERSION}/mcp-server-${os}-${arch}`.

**D3. Drift detection through a stamp file.** `setup.sh` writes the installed
`DIR_MCP_VERSION` to `.tools/stamps/dir-mcp` after installing and skips only when
the binary is executable and the stamp equals the pin. Alternatives: hash the
binary against `checksums.txt` on every run (correct but couples the skip check
to platform URL lookup and is the only tool doing it); always reinstall (breaks
the "already installed, nothing fetched" property the other tools have).

**D4. Install as `.tools/bin/dir-mcp`.** The release asset name is
`mcp-server-<os>-<arch>`; the recruiter looks up `dir-mcp`, as its own error
message states ("saved as dir-mcp").

**D5. Verify the sigstore bundle at pin time, not at install time.**
`update_checksums.bash` downloads each `mcp-server-<os>-<arch>` asset and its
`.sigstore.json`, runs `sigstore verify identity --bundle <bundle>
--cert-identity
https://github.com/agntcy/dir-mcp/.github/workflows/release.yml@refs/tags/v${DIR_MCP_VERSION}
--cert-oidc-issuer https://token.actions.githubusercontent.com <asset>`, and
only then records the SHA-256. The identity was read from the `v1.3.8-mcp.1`
bundle's certificate (SAN URI, issuer extension) and the command was tried on
the real darwin-arm64 asset: it prints `OK` for the genuine file and fails for a
wrong identity and for a one-byte-appended file (`Bundle message digest
mismatch`). `SIGSTORE_VERSION` is pinned in `versions.sh` (currently 4.5.1,
the newest release at least two weeks old) with a `datasource=pypi` Renovate
comment. Trust chain: signature checked when the pins are generated, SHA-256 on
every install. Alternatives: `cosign verify-blob` (a new pinned binary with four
platform checksums for one tool); `gh attestation verify` (needs `gh` and
authentication, and the release publishes sigstore bundles, not GitHub
attestations); verifying at every setup (network, TUF fetch and Python at
each run, for a guarantee the committed hashes already carry).

**D6. The verifier itself is hash-pinned.** `sigstore` and all its transitive
packages are pinned by SHA-256 in the committed
`scripts/lib/sigstore/requirements.txt`, generated by `uv pip compile
--universal --generate-hashes` from `sigstore==$SIGSTORE_VERSION`
(`task tools:sigstore-lock` regenerates it, like `task tools:npm-lock` does
for the npm tools). `update_checksums.bash` creates a throwaway venv
(`uv --no-config venv --python '>=3.10' --no-python-downloads`, so a machine
without a suitable interpreter fails loudly instead of downloading one), installs
with `uv --no-config pip install --require-hashes --no-deps --no-build -r <that
file>`, and runs the venv's `sigstore`; it refuses to run when the file's `sigstore==` pin differs
from `SIGSTORE_VERSION`. Measured on this machine: `uv tool run --with-requirements`
does NOT enforce the hashes (a file with corrupted hashes still installed and
ran), while `uv pip install --require-hashes` rejects the same file
(`Computed: sha256:...` mismatch) and installs the good one (`sigstore 4.5.1`,
`OK: dir-mcp` against the real bundle). Alternatives: `uv tool run` with the
version pin only (rejected: transitive packages unpinned, fails the repo's
"downloaded tools are SHA-256 verified" rule); vendoring the package (rejected:
unreviewable size).

## Risks / Trade-offs

- Renovate would propose `v1.3.8` as the "newer" version (published 2026-09-22
  next to `v1.3.8-mcp.1`), because `1.3.8-mcp.1` sorts below `1.3.8` in semver,
  and that would move the local binary off the line the compose image runs.
  SUPERSEDED by the owner on 2026-11-27 (newer plain releases must also be
  proposed): the comment now carries
  `versioning=regex:^(?<major>\d+)\.(?<minor>\d+)\.(?<patch>\d+)(?:-mcp\.(?<build>\d+))?$`,
  which orders `-mcp.<build>` above the plain release of the same version
  (checked against the installed Renovate engine) and proposes any newer release;
  see the `repo-tooling` main spec. Original decision, kept as history:
  the `# renovate:` comment on `DIR_MCP_VERSION` carried
  `versioning=regex:^(?<major>\d+)\.(?<minor>\d+)\.(?<patch>\d+)-mcp\.(?<build>\d+)$`
  (the repo's manager regex already reads a `versioning=` field before
  `extractVersion=`), so only `-mcp.<build>` releases are candidates. The compose
  and Dockerfile image reference (`ghcr.io/agntcy/dir-mcp:1.3.8-mcp.1`) is bumped
  by the Docker manager, which can still move independently; the pin and the
  image can drift by one Renovate cycle and are not grouped here.
- The sigstore lock regenerates its transitive packages on every Renovate
  Toolchain PR, so the generator passes `--exclude-newer "14 days"` (uv 0.12.23
  accepts the relative form; verified) to keep transitive packages as old as
  Renovate's `minimumReleaseAge` makes `sigstore` itself, and `--no-config` so a
  user `uv.toml` cannot steer the index the hashes are recorded from. (An earlier
  draft of this design deferred this as needing date arithmetic; that premise was
  wrong.)
- The verifier install passes `--no-build` and `--no-config`, so a missing wheel
  fails loudly instead of fetching unhashed build backends, and a user or system
  `uv.toml` cannot redirect the index. `UV_NO_VERIFY_HASHES=1` was tried and does
  not defeat `--require-hashes`.
- A stamp can lie if someone replaces the binary by hand. Acceptable: the stamp
  guards against stale pins, not against local tampering, and `checksums.txt`
  still guards every download.
- The unverified-`--version` situation is specific to this binary; if upstream
  adds a `--version` flag later, the stamp can be dropped in favor of
  `version_matches`.
