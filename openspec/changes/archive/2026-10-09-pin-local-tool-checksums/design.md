# Design

## Context

`setup.sh` installs tools two ways: a direct download (`FETCH <url>` then
`tar`/`install`) for seven tools, and `npm install --global --prefix
.tools` for openspec and renovate. Versions live in `scripts/lib/versions.sh`
with `# renovate:` annotations that a regex custom manager reads; the
`npm` manager is also enabled and grouped as "Frontend". Renovate is
self-hosted (the `Renovate` workflow runs the repo-local binary), so
`postUpgradeTasks` are available if the host allows the command.
See proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- Any byte difference in a downloaded archive or an npm package, relative
  to what was reviewed in a PR, fails `setup.sh`.
- Pins stay fresh through the existing Renovate flow with no manual step.
- One place describes each download URL.

**Non-Goals:**
- Verifying signatures or provenance (cosign, GPG, SLSA). Hashes are
  trust-on-first-use at bump time; the PR diff is the review point.
- Hash-pinning Node's own bundled npm, or tools installed outside
  `setup.sh` (e.g. `astral-sh/setup-uv` in the Renovate workflow, already
  SHA-pinned as an action).

## Decisions

**Checksums keyed by exact URL, in a flat `<sha256>  <url>` file.**
A version bump changes the URL, so a stale pin can never validate new
content, and a missing pin is distinguishable from a mismatch. The
`sha256sum` line shape keeps it greppable and diffable. Alternatives:
per-tool variables in `versions.sh` (28 values across 4 platforms would
swamp the file Renovate parses), or fetching upstream `SHASUMS` at install
time (defeats the purpose: it trusts the same origin as the archive).

**`FETCH_VERIFIED` downloads to a temp file, hashes, then streams.**
Nothing reaches `tar`/`install` unless verified, and call sites keep the
`FETCH ... >file` shape. Fails closed on both mismatch and missing pin,
the latter *before* any download.

**URLs live in `assets.sh`; the generator iterates the same function.**
Duplicating URL templates in `setup.sh` and the generator would let them
drift, producing pins `setup.sh` never looks up. A bats test asserts the
file's URL set equals `asset_url` over every tool and platform.

**`checksums.txt` is regenerated in full, not merged.** Re-downloading
everything (about 40 s) means an upstream asset silently changing under an
unchanged URL shows up as a diff in the Renovate PR instead of being
masked by a reused line.

**npm tools: versions stay in `versions.sh`; `package.json` is generated,
only the lockfile is committed; installed with `npm ci --ignore-scripts`
into `.tools/npm`, with `.tools/bin` symlinks.** `npm ci` verifies every
package's `integrity` and fails when the lockfile no longer matches the
generated `package.json`. A single place for every tool version (the
file a user reads to see what the repo runs) outweighs the convenience of
Renovate's npm manager. `npm_tools.sh` writes the `package.json`, shared by
`setup.sh` and `update_npm_lock.bash` so both produce the identical file.
`task tools:npm-lock` regenerates the lockfile starting from the committed
one (minimal transitive churn). Alternatives: a committed `package.json`
as the pin source for these two tools (a second version home, with the
Renovate npm manager needing its own packageRule), or a committed
`package.json` mirrored from `versions.sh` plus a sync test (two files to
keep equal). Install scripts are skipped: npm already refuses unlisted
ones, and renovate/openspec ran without them. Drift check: tool
`--version` equals the pin AND the committed lockfile is byte-identical
to the one copied into `.tools/npm` at last install.

**Renovate regenerates `checksums.txt` and the lockfile via
`postUpgradeTasks`** (`executionMode: branch`, so once per grouped PR,
`fileFilters` limited to those two files), attached to the custom regex
manager that already owns every version. The self-hosted workflow allows
exactly those two commands via `RENOVATE_ALLOWED_COMMANDS` (an anchored
regex), not a wildcard, since a
post-upgrade command runs repo code with the bot's token in scope.
Alternative: a CI check that fails the PR until a human runs the task -
kept as the fallback: `assets.bats` already fails on a stale file.

## Risks / Trade-offs

- [Hashes computed at bump time trust the network path of the Renovate
  runner] -> the PR diff is reviewed; for tools with published checksums
  (node, actionlint) a reviewer can cross-check.
- [A post-upgrade task runs repository code in Renovate's job] -> the
  command allowlist is one anchored path; the runner job has only the
  app token and `contents: read`.
- [Lockfile generated by a different npm than CI's] -> the lockfile is
  produced and consumed by the repo-pinned Node/npm only.
- [A tool dropping a platform asset breaks the generator for everyone] ->
  the generator fails loudly (`curl -f`) in the Renovate PR instead of on
  a developer's machine.

## Migration Plan

Land in one PR. Existing `.tools/` trees reinstall their npm
tools once (no lockfile copy present yet). Rollback: revert the PR.
